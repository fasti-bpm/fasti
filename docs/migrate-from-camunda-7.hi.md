# Camunda 7 से Fasti BPM पर माइग्रेशन

Fasti BPM, Camunda 7 Community Edition 7.24.0 पर आधारित है और Camunda 7 के
डेटाबेस के साथ संगत है। यह एक स्वतंत्र परियोजना है, जिसका Camunda Services GmbH से कोई संबंध नहीं है।

<a id="summary"></a>

## सारांश

यदि आप Camunda 7 **7.24** (Run, कंटेनर इमेज, Spring Boot स्टार्टर, Tomcat या
WildFly) चलाते हैं, तो Fasti **उसी डेटाबेस पर उसकी स्कीमा बदले बिना** चलता है: यह 7.24
स्कीमा को बिना बदलाव के उपयोग करता है और अपनी कोई तालिका, कॉलम या स्कीमा संस्करण नहीं लिखता। आप
पुराने नोड बदल सकते हैं, उनके साथ Fasti चला सकते हैं और Camunda 7.24 पर वापस जा सकते हैं (देखें
[रोलबैक](#rollback-to-camunda-724) और [सीमाएँ](#limits) में परीक्षित डेटाबेस)।

Camunda 7.23 और उससे पुराने संस्करणों के डेटाबेस को पहले SQL स्क्रिप्ट से 7.24 पर अपग्रेड करना होगा (देखें
[पुराने संस्करण](#older-versions-717723))। Fasti स्वयं कभी स्कीमा अपग्रेड नहीं करता; यह पुरानी स्कीमा पर
शुरू होने से इनकार करता है और चलाने के लिए आवश्यक स्क्रिप्ट के नाम बताता है।

<a id="steps-container-image"></a>

## चरण (कंटेनर इमेज)

1. **डेटाबेस का बैकअप लें।** नीचे दिए गए किसी भी चरण से स्कीमा नहीं बदलती, लेकिन प्रोडक्शन सिस्टम में
   कोई भी बदलाव करने से पहले बैकअप लेना अनिवार्य है।
2. **स्कीमा संस्करण जाँचें:** `select VERSION_ from ACT_GE_SCHEMA_LOG` — सबसे बड़ा मान
   `7.24.x` होना चाहिए।
3. पुराने नोड का **वर्तमान कॉन्फ़िगरेशन लिख लें**: `DB_*` वेरिएबल, इतिहास स्तर
   (`camunda.bpm.history-level`, `ACT_GE_PROPERTY.historyLevel`), REST प्रमाणीकरण
   (`camunda.bpm.run.auth.enabled`), प्राधिकरण (`camunda.bpm.authorization.enabled`),
   प्लगइन, LDAP/SSO, JVM समय क्षेत्र, पासवर्ड हैशिंग (`passwordEncryptor`, `saltGenerator`),
   तालिका प्रीफ़िक्स/स्कीमा।
4. **इमेज पुल करें** `fastidev/fasti-bpm:1.2.1` (या [distro/docker/README.md](../distro/docker/README.md)
   में बताए अनुसार स्रोत से बनाएँ)।
5. **उन्हीं `DB_*` वेरिएबल के साथ Fasti शुरू करें** (और वही `TZ` रखें)। Camunda Run के विपरीत,
   Fasti इमेज **डिफ़ॉल्ट रूप से REST प्रमाणीकरण अनिवार्य करती है और प्राधिकरण लागू करती है**: डेटाबेस
   खाते काम करते रहते हैं, लेकिन प्रत्येक REST क्लाइंट को Basic क्रेडेंशियल या bearer टोकन भेजना होगा,
   और `camunda-admin` से बाहर के उपयोगकर्ताओं को `ACT_RU_AUTHORIZATION` में अनुमतियाँ चाहिए (देखें
   [distro/docker/README.md](../distro/docker/README.md) में "डिफ़ॉल्ट रूप से सुरक्षित")।
   `FASTI_INSECURE_DEMO=true` केवल डेमो के लिए है। Fasti लॉग में यह लिखता है:
   `ENGINE-03115 Database schema version 7.24.0 matches this engine.`
6. **जाँचें:** किसी मौजूदा खाते से `/fasti/` पर साइन इन करें; जाँचें कि फ़िल्टर, कार्य, इंस्टेंस और इतिहास मौजूद हैं; `GET /engine-rest/task` (Basic क्रेडेंशियल के साथ) और `GET /actuator/health/readiness` कॉल करें।
7. **ट्रैफ़िक** (लोड बैलेंसर, DNS) को Fasti पर **स्थानांतरित करें**; पुराने नोड रोक दें या उन्हें चलते रहने दें (देखें
   [मिश्रित संचालन](#mixed-operation-with-camunda-7-nodes))।

Spring Boot स्टार्टर / Tomcat / WildFly: `org.camunda.bpm:camunda-*` आर्टिफ़ैक्ट को
उनके संबंधित `dev.fasti.platform:fasti-*` आर्टिफ़ैक्ट से बदलें और `camunda.bpm.*`, `bpm-platform.xml` तथा
`org.camunda.bpm.*` पैकेज बनाए रखें। क्लासपाथ पर दोनों इंजन jar न रखें; ऐसी स्थिति में Fasti शुरू होने से इनकार करता है (इस जाँच की सीमाओं के लिए
[embedding.hi.md](embedding.hi.md#startup-check) में "स्टार्टअप जाँच" देखें)।

> **Spring Boot स्टार्टर:** Fasti **Spring Boot 4.1** पर चलता है और इसके लिए **Java 17 या बाद का संस्करण** आवश्यक है।
> Camunda 7.24 स्टार्टर (Spring Boot 3.5) पर चल रहे एप्लिकेशन को आर्टिफ़ैक्ट बदलते समय ही Spring Boot 4.1 और
> Java 17+ पर भी जाना होगा। देखें
> [embedding.hi.md](embedding.hi.md#what-is-different-from-camunda-7240-ce) और
> [परिवर्तन विवरण](../CHANGELOG.md#changed)।

<a id="tomcat-and-wildfly-distributions"></a>

## Tomcat और WildFly वितरण

> **Camunda Run का डेटाबेस अपनाते समय आवश्यक** (या ऐसे सर्वर का डेटाबेस, जिसकी प्रक्रियाएँ
> REST API के माध्यम से डिप्लॉय की गई थीं): Tomcat और WildFly वितरण, Camunda 7 की तरह
> `jobExecutorDeploymentAware=true` बनाए रखते हैं। नोड पर पंजीकृत न होने वाले डिप्लॉयमेंट के
> जॉब (टाइमर, असिंक्रोनस निरंतरताएँ, पुनःप्रयास) **नहीं चलते, और किसी त्रुटि की सूचना भी नहीं मिलती**।
> शुरू करने से पहले, `conf/bpm-platform.xml` (Tomcat) में या
> `standalone.xml` (WildFly) की इंजन प्रॉपर्टी में `<property name="jobExecutorDeploymentAware">false</property>` सेट करें।
> यदि अन्य नोड अपनी Java क्लास वाले प्रोसेस एप्लिकेशन चलाते हैं, तो
> `true` बनाए रखें (देखें [मिश्रित संचालन](#mixed-operation-with-camunda-7-nodes))।

Camunda 7.24 के Tomcat/WildFly वितरणों की तुलना में:

- **REST API के लिए प्रमाणीकरण आवश्यक है** (संगतता प्रभावित करने वाला बदलाव)। `/engine-rest` पर `camunda-auth`
  फ़िल्टर (HTTP Basic) सक्षम है: प्रत्येक REST क्लाइंट को किसी इंजन उपयोगकर्ता का उपयोगकर्ता नाम और पासवर्ड भेजना होगा; अन्यथा उसे 401 मिलता है; केवल इंजनों की सूची (`/engine`) खुली रहती है।
  माइग्रेशन से पहले, उन REST क्लाइंट, एक्सटर्नल टास्क वर्कर और स्क्रिप्ट में क्रेडेंशियल कॉन्फ़िगर करें जो REST
  API को बिना प्रमाणीकरण के कॉल करते हैं। OpenID Connect bearer टोकन (`fasti-oidc.properties`,
  `fasti.security.oidc.rest.bearer-enabled=true`) भी काम करते हैं: वैध टोकन वाले अनुरोधों को पासवर्ड की आवश्यकता नहीं होती। प्रमाणीकरण बंद करने के लिए (**अनुशंसित नहीं**), `engine-rest` WAR के
  `WEB-INF/web.xml` से `camunda-auth` फ़िल्टर और उसकी `filter-mapping` हटाएँ।
- **कोई डिफ़ॉल्ट उपयोगकर्ता नहीं** (संगतता प्रभावित करने वाला बदलाव)। इनवॉइस उदाहरण अब डिप्लॉय नहीं किया जाता, इसलिए यह
  `demo/demo` (व्यवस्थापक), `john`, `mary` और `peter` नहीं बनाता; इसका WAR
  `examples/camunda-invoice.war` है, जिसे आज़माने के लिए `webapps/` (Tomcat) या
  `standalone/deployments/` (WildFly) में कॉपी करें। खाली डेटाबेस पर `/fasti/` खोलें
  और सेटअप पृष्ठ पर पहला व्यवस्थापक बनाएँ; Camunda 7 डेटाबेस पर
  मौजूदा खातों का उपयोग करें।
- **क्लासिक Cockpit, Tasklist, Admin और Welcome उपलब्ध नहीं कराए जाते** (संगतता प्रभावित करने वाला बदलाव), जैसा कि
  इमेज में भी है: उनके पृष्ठ और बुकमार्क नए UI के संबंधित अनुभाग पर ले जाते हैं, उनकी फ़ाइलों के अनुरोध 404 लौटाते हैं। उन्हें अस्थायी रूप से फिर सक्षम करने के लिए (अप्रचलित, आगे हटा दिए जाएँगे), इनमें से किसी एक सेटिंग का उपयोग करें:
  `CATALINA_OPTS` (Tomcat) या `JAVA_OPTS` (WildFly) में `-Dfasti.webapp.classic.enabled=true`,
  पर्यावरण वेरिएबल `FASTI_CLASSIC_WEBAPPS=true`, या वेब एप्लिकेशन के `WEB-INF/web.xml` में
  संदर्भ पैरामीटर `fasti.webapp.classic.enabled`।

<a id="what-is-identical"></a>

## क्या समान है

- स्कीमा और `ACT_GE_PROPERTY`/`ACT_GE_SCHEMA_LOG` की पंक्तियाँ (Fasti कोई संस्करण पंक्ति नहीं जोड़ता),
  इंस्टॉलेशन आईडी, आईडी जनरेशन (Run/Spring Boot में `StrongUuidGenerator`, इंजन का
  डिफ़ॉल्ट `DbIdGenerator`)।
- पासवर्ड: Camunda 7 की तरह 16-बाइट salt के साथ SHA-512; मौजूदा उपयोगकर्ता साइन इन कर सकते हैं, और
  Fasti पर बदले गए पासवर्ड Camunda 7 पर काम करते हैं।
- `/engine-rest` पर REST API: वही एंडपॉइंट, पैरामीटर और पेलोड, साथ में अतिरिक्त एंडपॉइंट
  (प्रमाणीकरण और कुछ स्टेटस कोड अलग हैं, देखें [क्या अलग है](#what-differs)), एक्सटर्नल टास्क
  (`fetchAndLock`, लॉन्ग पोलिंग), Java और JS क्लाइंट, `JSESSIONID`, `XSRF-TOKEN`/`X-XSRF-TOKEN`, `camunda.bpm.*`
  प्रॉपर्टी, `camunda:` BPMN नेमस्पेस।
- क्लासिक Tasklist के फ़िल्टर (`color`, `description`, `priority`, `refresh`, `variables`,
  `showUndefinedVariable`) नई Tasklist द्वारा उसी प्रारूप में पढ़े और लिखे जाते हैं।

<a id="what-differs"></a>

## क्या अलग है

- वेब एप्लिकेशन `/fasti/app/...` पर उपलब्ध हैं; `/camunda/...` वहाँ रीडायरेक्ट करता है (301/308)। यदि आपका प्रॉक्सी केवल `/camunda` उपलब्ध कराता है, तो `/fasti` भी उपलब्ध कराएँ या `FASTI_WEBAPP_PATH=/camunda` सेट करें। रूट
  नया वेब एप्लिकेशन खोलता है (`fasti.webapp.default-app: welcome` से Welcome वापस आता है, लेकिन
  इमेज में नहीं, जहाँ क्लासिक एप्लिकेशन बंद हैं)।
- **संगतता प्रभावित करने वाला बदलाव, कंटेनर इमेज:** क्लासिक Cockpit, Tasklist, Admin और Welcome
  उपलब्ध नहीं कराए जाते, क्योंकि AngularJS 1.8.2 और Bootstrap 3 का समर्थन समाप्त हो चुका है। उनके पृष्ठ और बुकमार्क,
  `/camunda/app/` के अंतर्गत भी, नए वेब UI के संबंधित अनुभाग (`#/cockpit`,
  `#/tasklist`, `#/admin`) पर रीडायरेक्ट करते हैं; उनकी फ़ाइलों के अनुरोध 404 लौटाते हैं। उपयोगकर्ताओं को नए वेब UI पर ले जाएँ;
  `FASTI_CLASSIC_WEBAPPS=true` संक्रमण अवधि के दौरान चेतावनी के साथ क्लासिक एप्लिकेशन फिर उपलब्ध कराता
  है। Tomcat और WildFly भी उन्हें उपलब्ध नहीं कराते (देखें
  [Tomcat और WildFly वितरण](#tomcat-and-wildfly-distributions))। Run zip और
  Spring Boot स्टार्टर अब भी उन्हें उपलब्ध कराते हैं, लेकिन वे अप्रचलित हैं और बाद की किसी
  रिलीज़ में हटा दिए जाएँगे (`fasti.webapp.classic.enabled: false` उन्हें पहले ही बंद कर देता है)।
- पुरानी स्कीमा होने पर, बाद में विफल होने के बजाय Fasti `ENGINE-03111` के साथ शुरू होने से इनकार करता है
  (फिर भी शुरू करने के लिए `FASTI_SCHEMA_VERSION_CHECK=warn`)।
- क्वेरी और फ़िल्टर में एक्सप्रेशन एक अनुमति सूची तक सीमित हैं (तारीख फ़ंक्शन, वर्तमान
  उपयोगकर्ता); कस्टम bean या फ़ंक्शन का उपयोग करने वाले फ़िल्टर के लिए उन्हें इंजन कॉन्फ़िगरेशन
  प्रॉपर्टी `allowedExpressionFunctionsInQueries`, `allowedExpressionBeansInQueries` और
  `allowedExpressionPropertiesInQueries` में घोषित करना होगा।
- REST API का व्यवहार: कंटेनर इमेज और Tomcat तथा WildFly वितरणों में इंजनों की सूची (`/engine`)
  को छोड़कर हर अनुरोध के लिए Basic क्रेडेंशियल या bearer टोकन आवश्यक है, इसलिए REST क्लाइंट और
  एक्सटर्नल टास्क वर्कर को उन्हें भेजने के लिए कॉन्फ़िगर करना होगा (उनका कोड नहीं बदलता)। हर
  वितरण में, अनुमति सूची से बाहर के क्वेरी एक्सप्रेशन `400` के साथ अस्वीकार किए जाते हैं; अनुमति के
  बिना टास्क अटैचमेंट और टिप्पणियाँ पढ़ने या बदलने पर `403` मिलता है (प्राधिकरण जाँच चालू होने
  पर); कुछ अमान्य अनुरोध जिनका उत्तर पहले `500` था, अब `400` पाते हैं (पार्स न हो सकने वाले
  डिप्लॉयमेंट संसाधन, प्रतिबंधित Java serialization प्रारूप में वेरिएबल, गलत प्रकार के क्वेरी
  पैरामीटर, पासवर्ड नीति का उल्लंघन करने वाले पासवर्ड)। देखें
  [Differences from Camunda 7](api/README.md#differences-from-camunda-7)।
- इमेज के डिफ़ॉल्ट: स्कीमा अपडेट `false` (नए डेटाबेस के लिए `FASTI_DB_SCHEMA_UPDATE=true`); कोई
  डेमो उपयोगकर्ता, इनवॉइस उदाहरण या "सभी कार्य" फ़िल्टर नहीं; CORS बंद (`FASTI_CORS_ALLOWED_ORIGINS=*`
  इसे फिर सक्षम करता है); `/actuator/health` जोड़ा गया; फ़ाइलें `/fasti` के अंतर्गत (`/camunda/configuration`
  पर माउंट की गई फ़ाइलें भी पढ़ी जाती हैं); `--swaggerui` नहीं।
- OAuth2/OIDC: समूह claim में `camunda-admin` अब अपने आप व्यवस्थापक अधिकार नहीं देता
  (`fasti.security.oidc.groups.admin`); `group-name-delimiter` को अक्षरशः पाठ माना जाता है, regex नहीं;
  लॉगआउट के लिए समान ओरिजिन से POST आवश्यक है।
- नई Tasklist: `refresh` के बिना फ़िल्टर अपने आप रीफ़्रेश होता है।
- Run jar का नाम `fasti-bpm-run-core.jar` है।
- 7.24.0 की तुलना में सुरक्षा सुधार (अटैचमेंट/टिप्पणी प्राधिकरण, प्रारंभिक सेटअप, ...) के कारण पहले सफल होने वाली कुछ कॉल 403 लौटा सकती हैं; देखें [CHANGELOG](../CHANGELOG.md) के *Security* खंड और <https://fasti.dev/security>।

<a id="rollback-to-camunda-724"></a>

## Camunda 7.24 पर वापस लौटना

Fasti रोकें और उसी डेटाबेस पर Camunda 7.24 नोड फिर शुरू करें। Fasti पर किया गया
सभी काम वहाँ दिखाई देता है। जो शेष रहता है: `ACT_ID_INFO` में `fasti.prefs.*` पंक्तियाँ (नए
वेब UI की प्राथमिकताएँ, जिन्हें Camunda 7 अनदेखा करता है) और नई Tasklist द्वारा सहेजे गए उन फ़िल्टर पर `refresh: true`,
जिनमें यह पहले अनुपस्थित था। केवल Fasti में उपलब्ध सुविधाओं का उपयोग करने वाली डिप्लॉय की गई प्रक्रियाएँ Camunda 7 पर नहीं चलतीं।

<a id="mixed-operation-with-camunda-7-nodes"></a>

## Camunda 7 नोड के साथ मिश्रित संचालन

Fasti और Camunda 7.24 एक ही डेटाबेस पर एक साथ चल सकते हैं (परीक्षित: दोनों एक-दूसरे का
डेटा देखते हैं और जॉब किसी भी नोड पर चलते हैं)। आवश्यकताएँ:

- **समान इतिहास स्तर** (इमेज संग्रहीत स्तर का उपयोग करती है), **समान JVM समय क्षेत्र**,
  समान पासवर्ड सेटिंग और तालिका प्रीफ़िक्स;
- **जॉब एक्ज़ीक्यूटर:** डिफ़ॉल्ट रूप से Fasti (इमेज, Run, Spring Boot), Run की तरह हर डिप्लॉयमेंट के जॉब उठाता है।
  Tomcat और WildFly वितरणों में डिफ़ॉल्ट `jobExecutorDeploymentAware=true` है (जैसा कि Camunda
  7 में है): उस नोड पर पंजीकृत न होने वाले डिप्लॉयमेंट के जॉब (टाइमर, असिंक्रोनस निरंतरताएँ, पुनःप्रयास),
  जिनमें अंतिम रीस्टार्ट से पहले Run या REST के माध्यम से किए गए डिप्लॉयमेंट भी शामिल हैं, **नहीं
  चलते**; Run का डेटाबेस अपनाते समय, इसे `conf/bpm-platform.xml`
  (Tomcat) या `standalone.xml` (WildFly) में `false` सेट करें। यदि पुराने नोड ऐसे प्रोसेस एप्लिकेशन चलाते हैं जिनकी क्लास Fasti में नहीं हैं (`JavaDelegate`, लिसनर, bean),
  तो Fasti उनके जॉब उठा लेगा, जो फिर विफल होंगे और इंसिडेंट उत्पन्न करेंगे। ऐसी स्थिति में
  Fasti पर `FASTI_JOB_EXECUTOR_ENABLED=false` सेट करें, या **हर** नोड को डिप्लॉयमेंट के प्रति सजग बनाएँ (नोड का
  जॉब एक्ज़ीक्यूटर केवल उसी नोड पर पंजीकृत डिप्लॉयमेंट के जॉब चलाता है; REST के माध्यम से किया गया डिप्लॉयमेंट
  रीस्टार्ट होने तक केवल उसे प्राप्त करने वाले नोड पर पंजीकृत रहता है)। सिंक्रोनस REST कॉल (कार्य पूरा करना,
  इंस्टेंस शुरू करना) अब भी उन्हें प्राप्त करने वाले नोड पर डेलीगेट चलाती हैं — ऐसी
  प्रक्रियाओं को Fasti पर रूट न करें;
- **लोड बैलेंसर:** वेब एप्लिकेशन के लिए स्टिकी सेशन; Basic प्रमाणीकरण वाली REST कॉल को इनकी आवश्यकता नहीं है;
- क्लासिक वेब एप्लिकेशन (Camunda 7 नोड पर, या
  `FASTI_CLASSIC_WEBAPPS=true` वाले Fasti पर) और नया वेब एप्लिकेशन फ़िल्टर और उपयोगकर्ता साझा करते हैं।

<a id="older-versions-717723"></a>

## पुराने संस्करण (7.17–7.23)

बैकअप लें; `sql/upgrade/<db>_engine_<from>_to_<to>.sql` को क्रम से 7.24 तक चलाएँ, जिसमें
आपके वर्तमान माइनर संस्करण की बाकी पैच स्क्रिप्ट भी शामिल हों (ये `configuration/sql/upgrade` में मिलती हैं, इमेज में
`/fasti/configuration/sql/upgrade` पर); जाँचें कि `ACT_GE_SCHEMA_LOG` में `7.24.0` मौजूद है;
Fasti शुरू करें। 7.22 → 7.24 का उदाहरण: `postgres_engine_7.22_to_7.23.sql`, फिर
`postgres_engine_7.23_to_7.24.sql`। 7.24 से पुराने Camunda नोड अपग्रेड की गई
स्कीमा पर चलते नहीं रहने चाहिए, सिवाय Camunda के रोलिंग अपडेट नियमों के अंतर्गत (केवल एक माइनर संस्करण, और
पुराने नोड नई सुविधाओं का उपयोग नहीं कर सकते)।

<a id="performance"></a>

## प्रदर्शन

इमेज अब जॉब एक्ज़ीक्यूटर और कनेक्शन पूल के लिए Camunda Run के डिफ़ॉल्ट नहीं अपनाती (Fasti 1.1 तक अपनाती थी): इसमें 10 जॉब थ्रेड, 10 की कतार और हर अधिग्रहण में 10 जॉब होते हैं (Camunda Run: कोर 3, अधिकतम 10, कतार 3, हर अधिग्रहण में 3), और अधिकतम 20 कनेक्शन का पूल, जिनमें से निष्क्रिय अवस्था में 10 खुले रहते हैं (Camunda Run: 10)। डेटाबेस की कनेक्शन सीमा सभी नोड्स के पूल को मिलाकर तय करें, Camunda 7 नोड्स सहित ([रनटाइम ट्यूनिंग](tuning-runtime.md), अंग्रेज़ी में)। यदि आपने अपने पिछले Camunda 7 इंस्टॉलेशन के कनेक्शन पूल या जॉब एक्ज़ीक्यूटर को ट्यून किया था, तो वे मान यहाँ भी लागू करें (`FASTI_DB_CONN_MAXACTIVE`, `FASTI_DB_CONN_MINIDLE`, `CAMUNDA_BPM_JOB_EXECUTION_*`); अधिक मार्गदर्शन `distro/docker/README.md` के "प्रदर्शन ट्यूनिंग" में है। Fasti स्कीमा के इंडेक्स कभी अपने आप नहीं बदलता; बड़े डेटाबेस के लिए यह वैकल्पिक इंडेक्स स्क्रिप्ट के रूप में देता है जिन्हें कोई एडमिनिस्ट्रेटर चलाता है (`/fasti/configuration/sql/optional/<database>_fasti_perf_indexes_create.sql`, देखें [performance.md](performance.md)); ये Camunda 7.24 नोड्स के साथ सुरक्षित हैं और संबंधित `_drop.sql` से हटाए जाते हैं।

<a id="limits"></a>

## सीमाएँ

- केवल 7.24 Community Edition स्कीमा समर्थित है; Enterprise पैच स्कीमा का परीक्षण नहीं हुआ है।
- कंटेनर इमेज के साथ परीक्षण किया गया (Camunda Run 7.24.0 डेटाबेस बनाता है और उसमें प्रारंभिक डेटा भरता है → Fasti
  उसे अपनाता है → वापस Run पर → दोनों एक साथ):

  | डेटाबेस | ड्राइवर | डेटाबेस अपनाना | वापस लौटना | मिश्रित संचालन | अपग्रेड 7.23 → 7.24 |
  |---|---|---|---|---|---|
  | PostgreSQL 16 | साथ उपलब्ध | सफल | सफल | सफल | परीक्षण नहीं हुआ |
  | MariaDB 11.8 | MariaDB Connector/J (साथ उपलब्ध) या MySQL Connector/J | सफल | सफल | सफल | सफल |
  | MySQL 8.4 | साथ उपलब्ध | सफल | — | सफल | सफल |
  | SQL Server 2022 (Developer) | साथ उपलब्ध (`encrypt=false`) | सफल | सफल | सफल | परीक्षण नहीं हुआ |
  | Oracle Database 23ai Free | `FASTI_EXTRA_LIB` के माध्यम से `ojdbc11` | सफल | सफल | सफल | परीक्षण नहीं हुआ |
  | DB2 | — | परीक्षण नहीं हुआ | | | |

  इसके अतिरिक्त: MariaDB (MariaDB Connector/J) पर दो Fasti नोड ने समान कार्य पूरे करते हुए और समानांतर रूप से एक्सटर्नल टास्क प्राप्त करते हुए कुछ भी नहीं खोया या दोहराया; प्रतिस्पर्धा में असफल ट्रांज़ैक्शन को ऑप्टिमिस्टिक लॉकिंग त्रुटि मिली। MySQL/MariaDB के लिए `transaction-isolation=READ-COMMITTED` आवश्यक है। MySQL पर
  प्रत्येक इंजन को अपना अलग डेटाबेस दें: इंजन (Camunda Run और Fasti दोनों) उन सभी डेटाबेस में
  तालिकाएँ खोजता है जिन्हें खाता देख सकता है।
- Camunda 7 के लिए बनाए गए प्लगइन और प्रोसेस एप्लिकेशन को Fasti के भीतर चलाने के लिए Fasti
  आर्टिफ़ैक्ट के विरुद्ध फिर से बिल्ड करना होगा। REST क्लाइंट और एक्सटर्नल टास्क क्लाइंट के कोड में
  बदलाव की आवश्यकता नहीं है; कंटेनर इमेज, Tomcat या WildFly के साथ उन्हें Basic क्रेडेंशियल या
  bearer टोकन भेजने के लिए कॉन्फ़िगर करना होगा।
- स्कीमा जाँच केवल `ACT_GE_SCHEMA_LOG` पढ़ती है; यह कॉलम की तुलना नहीं करती।
