# การย้ายจาก Camunda 7 ไปยัง Fasti BPM

Fasti BPM สร้างบน Camunda 7 Community Edition 7.24.0 และเข้ากันได้กับฐานข้อมูล Camunda 7
โครงการนี้เป็นโครงการอิสระ และไม่มีความเกี่ยวข้องกับ Camunda Services GmbH

<a id="summary"></a>

## สรุป

หากคุณใช้ Camunda 7 **7.24** (Run, อิมเมจคอนเทนเนอร์, Spring Boot starter, Tomcat หรือ
WildFly) Fasti สามารถทำงานบน **ฐานข้อมูลเดิมนั้นได้โดยไม่เปลี่ยนแปลงสคีมา** โดยใช้สคีมา 7.24
ตามเดิม และไม่เขียนตาราง คอลัมน์ หรือเวอร์ชันสคีมาของตนเองเพิ่มเติม คุณสามารถแทนที่
โหนดเดิม รัน Fasti ควบคู่ไปกับโหนดเหล่านั้น และกลับไปใช้ Camunda 7.24 ได้ (ดู
[การย้อนกลับ](#rollback-to-camunda-724) และฐานข้อมูลที่ทดสอบแล้วใน[ข้อจำกัด](#limits))

ฐานข้อมูลของ Camunda 7.23 และเวอร์ชันก่อนหน้าต้องอัปเกรดเป็น 7.24 ด้วยสคริปต์ SQL ก่อน (ดู
[เวอร์ชันเก่า](#older-versions-717723)) Fasti จะไม่อัปเกรดสคีมาด้วยตนเอง แต่จะปฏิเสธการ
เริ่มทำงานบนสคีมาเก่าและระบุชื่อสคริปต์ที่ต้องเรียกใช้

<a id="steps-container-image"></a>

## ขั้นตอน (อิมเมจคอนเทนเนอร์)

1. **สำรองฐานข้อมูล** แม้ขั้นตอนด้านล่างจะไม่เปลี่ยนแปลงสคีมา แต่จำเป็นต้องสำรองข้อมูล
   ก่อนเปลี่ยนแปลงระบบที่ใช้งานจริงทุกครั้ง
2. **ตรวจสอบเวอร์ชันสคีมา:** `select VERSION_ from ACT_GE_SCHEMA_LOG` — ค่าสูงสุด
   ต้องเป็น `7.24.x`
3. **บันทึกการกำหนดค่าปัจจุบัน** ของโหนดเดิม: ตัวแปร `DB_*`, ระดับประวัติ
   (`camunda.bpm.history-level`, `ACT_GE_PROPERTY.historyLevel`), การยืนยันตัวตน REST
   (`camunda.bpm.run.auth.enabled`), การกำหนดสิทธิ์ (`camunda.bpm.authorization.enabled`),
   ปลั๊กอิน, LDAP/SSO, เขตเวลาของ JVM, การแฮชรหัสผ่าน (`passwordEncryptor`, `saltGenerator`),
   คำนำหน้าตาราง/สคีมา
4. **ดึงอิมเมจ** `fastidev/fasti-bpm:1.3.2` (หรือสร้างจากซอร์สโค้ดตามที่อธิบายไว้ใน
   [distro/docker/README.md](../distro/docker/README.md))
5. **เริ่ม Fasti ด้วยตัวแปร `DB_*` เดิม** (และ `TZ` เดิม) อิมเมจ Fasti ต่างจาก Camunda Run ตรงที่
   **กำหนดให้ต้องยืนยันตัวตน REST และบังคับใช้การกำหนดสิทธิ์โดยค่าเริ่มต้น**: บัญชีในฐานข้อมูล
   ยังคงใช้งานได้ แต่ไคลเอนต์ REST ทุกตัวต้องส่งข้อมูลรับรองแบบ Basic หรือโทเค็น bearer
   และผู้ใช้ที่ไม่ได้อยู่ใน `camunda-admin` ต้องได้รับสิทธิ์ใน `ACT_RU_AUTHORIZATION` (ดู “ปลอดภัยโดย
   ค่าเริ่มต้น” ใน [distro/docker/README.md](../distro/docker/README.md))
   `FASTI_INSECURE_DEMO=true` มีไว้สำหรับการสาธิตเท่านั้น Fasti จะบันทึกข้อความ
   `ENGINE-03115 Database schema version 7.24.0 matches this engine.`
6. **ตรวจสอบ:** ลงชื่อเข้าใช้ที่ `/fasti/` ด้วยบัญชีที่มีอยู่ ตรวจสอบว่าตัวกรอง งาน อินสแตนซ์ และประวัติยังอยู่ เรียก `GET /engine-rest/task` (พร้อมข้อมูลรับรองแบบ Basic) และ `GET /actuator/health/readiness`
7. **ย้ายทราฟฟิก** (โหลดบาลานเซอร์, DNS) ไปยัง Fasti หยุดโหนดเดิมหรือปล่อยให้ทำงานต่อไป (ดู
   [การทำงานร่วมกัน](#mixed-operation-with-camunda-7-nodes))

Spring Boot starter / Tomcat / WildFly: แทนที่อาร์ติแฟกต์ `org.camunda.bpm:camunda-*` ด้วย
`dev.fasti.platform:fasti-*` ที่ตรงกัน และคง `camunda.bpm.*`, `bpm-platform.xml` และ
แพ็กเกจ `org.camunda.bpm.*` ไว้ อย่าเก็บไฟล์ jar ของเอนจินทั้งสองไว้บน classpath เพราะ Fasti จะปฏิเสธการเริ่มทำงาน (สำหรับข้อจำกัดของการตรวจสอบนี้ ดู “การตรวจสอบเมื่อเริ่มทำงาน” ใน
[embedding.th.md](embedding.th.md#startup-check))

> **Spring Boot starter:** Fasti ทำงานบน **Spring Boot 4.1** และต้องใช้ **Java 17 หรือใหม่กว่า**
> แอปพลิเคชันที่ใช้ Camunda 7.24 starter (Spring Boot 3.5) ต้องย้ายไปใช้ Spring Boot 4.1 และ
> Java 17+ พร้อมกับการเปลี่ยนอาร์ติแฟกต์ ดู
> [embedding.th.md](embedding.th.md#what-is-different-from-camunda-7240-ce) และ
> [บันทึกการเปลี่ยนแปลง](../CHANGELOG.md#changed)

## ชุดแจกจ่าย Tomcat และ WildFly

> **จำเป็นเมื่อรับช่วงฐานข้อมูลของ Camunda Run** (หรือของเซิร์ฟเวอร์ที่มีการ
> ดีพลอยกระบวนการผ่าน REST API): ชุดแจกจ่าย Tomcat และ WildFly คงค่า
> `jobExecutorDeploymentAware=true` เช่นเดียวกับ Camunda 7 งาน (ตัวตั้งเวลา, การทำงานต่อแบบอะซิงโครนัส, การลองใหม่)
> ของการดีพลอยที่ไม่ได้ลงทะเบียนบนโหนด **จะไม่ทำงาน และไม่มีการรายงานข้อผิดพลาด**
> ก่อนเริ่มทำงาน ให้ตั้งค่า `<property name="jobExecutorDeploymentAware">false</property>` ใน
> `conf/bpm-platform.xml` (Tomcat) หรือในพร็อพเพอร์ตีของเอนจินใน `standalone.xml` (WildFly)
> คงค่า `true` ไว้หากโหนดอื่นรันแอปพลิเคชันกระบวนการที่มีคลาส Java ของตนเอง (ดู
> [การทำงานร่วมกัน](#mixed-operation-with-camunda-7-nodes))

เมื่อเทียบกับชุดแจกจ่าย Tomcat/WildFly ของ Camunda 7.24:

- **REST API กำหนดให้ต้องยืนยันตัวตน** (การเปลี่ยนแปลงที่ไม่เข้ากันกับการใช้งานเดิม) `/engine-rest` เปิดใช้ตัวกรอง `camunda-auth`
  (HTTP Basic): ไคลเอนต์ REST ทุกตัวต้องส่งชื่อผู้ใช้และรหัสผ่านของผู้ใช้เอนจิน มิฉะนั้นจะได้รับ 401 โดยมีเพียงรายการเอนจิน (`/engine`) ที่ยังเปิดให้เข้าถึงได้
  กำหนดค่าข้อมูลรับรองในไคลเอนต์ REST, ตัวประมวลผลงานภายนอก และสคริปต์ที่เรียก REST
  API โดยไม่ยืนยันตัวตนก่อนเปลี่ยนมาใช้ Fasti โทเค็น bearer ของ OpenID Connect (`fasti-oidc.properties`,
  `fasti.security.oidc.rest.bearer-enabled=true`) ก็ใช้งานได้เช่นกัน: คำขอที่มีโทเค็นถูกต้องไม่จำเป็นต้องใช้รหัสผ่าน หากต้องการปิดการยืนยันตัวตน (**ไม่แนะนำ**) ให้ลบ
  ตัวกรอง `camunda-auth` และ `filter-mapping` ของตัวกรองนั้นออกจาก `WEB-INF/web.xml` ของ WAR `engine-rest`
- **ไม่มีผู้ใช้เริ่มต้น** (การเปลี่ยนแปลงที่ไม่เข้ากันกับการใช้งานเดิม) ตัวอย่างใบแจ้งหนี้จะไม่ถูกดีพลอยอีกต่อไป จึงไม่
  สร้าง `demo/demo` (ผู้ดูแลระบบ), `john`, `mary` และ `peter` โดย WAR ของตัวอย่างอยู่ที่
  `examples/camunda-invoice.war` ให้คัดลอกไปยัง `webapps/` (Tomcat) หรือ
  `standalone/deployments/` (WildFly) เพื่อทดลองใช้งาน สำหรับฐานข้อมูลว่าง ให้เปิด `/fasti/`
  และสร้างผู้ดูแลระบบคนแรกในหน้าตั้งค่า สำหรับฐานข้อมูล Camunda 7 ให้ใช้
  บัญชีที่มีอยู่
- **ไม่มีการให้บริการ Cockpit, Tasklist, Admin และ Welcome แบบคลาสสิก** (การเปลี่ยนแปลงที่ไม่เข้ากันกับการใช้งานเดิม) เช่นเดียวกับใน
  อิมเมจ: หน้าเว็บและบุ๊กมาร์กของแอปพลิเคชันเหล่านี้จะนำไปยังส่วนที่ตรงกันใน UI ใหม่ ส่วนคำขอไฟล์ของแอปพลิเคชันเหล่านี้จะได้รับ 404 หากต้องการเปิดใช้อีกครั้งชั่วคราว (เลิกแนะนำให้ใช้และจะถูกนำออก) ให้ใช้การตั้งค่าอย่างใดอย่างหนึ่งต่อไปนี้:
  `-Dfasti.webapp.classic.enabled=true` ใน `CATALINA_OPTS` (Tomcat) หรือ `JAVA_OPTS` (WildFly),
  ตัวแปรสภาพแวดล้อม `FASTI_CLASSIC_WEBAPPS=true` หรือพารามิเตอร์บริบท
  `fasti.webapp.classic.enabled` ใน `WEB-INF/web.xml` ของเว็บแอปพลิเคชัน

## สิ่งที่เหมือนเดิม

- สคีมาและแถวใน `ACT_GE_PROPERTY`/`ACT_GE_SCHEMA_LOG` (Fasti ไม่เพิ่มแถวเวอร์ชัน),
  รหัสการติดตั้ง, การสร้างรหัส (`StrongUuidGenerator` ใน Run/Spring Boot และ
  `DbIdGenerator` ซึ่งเป็นค่าเริ่มต้นของเอนจิน)
- รหัสผ่าน: SHA-512 พร้อม salt ขนาด 16 ไบต์เช่นเดียวกับ Camunda 7 ผู้ใช้เดิมสามารถลงชื่อเข้าใช้ได้ และ
  รหัสผ่านที่เปลี่ยนบน Fasti สามารถใช้บน Camunda 7 ได้
- REST API ที่ `/engine-rest`: เอนด์พอยต์ พารามิเตอร์ และเพย์โหลดเดิม พร้อมเอนด์พอยต์เพิ่มเติม
  (การยืนยันตัวตนและรหัสสถานะบางรายการแตกต่างออกไป ดู[สิ่งที่แตกต่าง](#what-differs)), งานภายนอก
  (`fetchAndLock`, long polling), ไคลเอนต์ Java และ JS, `XSRF-TOKEN`/`X-XSRF-TOKEN`, พร็อพเพอร์ตี `camunda.bpm.*`
  และเนมสเปซ BPMN `camunda:` คุกกี้เซสชันในดิสทริบิวชัน Tomcat และ WildFly ชื่อ `JSESSIONID` ส่วน Run และคอนเทนเนอร์อิมเมจใช้ชื่อ `FASTI_SESSION` ตั้งแต่ 1.3.2 (`server.servlet.session.cookie.name`) เพื่อไม่ให้ชนกับ Camunda 7 Run บนโฮสต์เดียวกัน สคริปต์ที่ค้นหาคุกกี้ตามชื่อต้องเปลี่ยนไปใช้ชื่อใหม่
- ตัวกรองจาก Tasklist แบบคลาสสิก (`color`, `description`, `priority`, `refresh`, `variables`,
  `showUndefinedVariable`) จะถูกอ่านและเขียนในรูปแบบเดิมโดย Tasklist ใหม่

## สิ่งที่แตกต่าง

- เว็บแอปพลิเคชันอยู่ที่ `/fasti/app/...` โดย `/camunda/...` จะเปลี่ยนเส้นทางไปที่นั่น (301/308) หากพร็อกซีของคุณเปิดให้เข้าถึงเฉพาะ `/camunda` ให้เปิด `/fasti` ด้วย หรือตั้งค่า `FASTI_WEBAPP_PATH=/camunda` เส้นทางราก
  จะเปิดเว็บแอปพลิเคชันใหม่ (`fasti.webapp.default-app: welcome` จะนำ Welcome กลับมา ยกเว้น
  ในอิมเมจซึ่งปิดแอปพลิเคชันแบบคลาสสิกไว้)
- **การเปลี่ยนแปลงที่ไม่เข้ากันกับการใช้งานเดิมในอิมเมจคอนเทนเนอร์:** ไม่มีการให้บริการ Cockpit, Tasklist, Admin และ Welcome
  แบบคลาสสิก เนื่องจาก AngularJS 1.8.2 และ Bootstrap 3 สิ้นสุดการสนับสนุนแล้ว หน้าเว็บและบุ๊กมาร์กของแอปพลิเคชันเหล่านี้
  รวมถึงที่อยู่ภายใต้ `/camunda/app/` จะเปลี่ยนเส้นทางไปยังส่วนที่ตรงกันในเว็บ UI ใหม่ (`#/cockpit`,
  `#/tasklist`, `#/admin`) ส่วนคำขอไฟล์ของแอปพลิเคชันเหล่านี้จะได้รับ 404 ให้ย้ายผู้ใช้ไปยังเว็บ UI ใหม่
  `FASTI_CLASSIC_WEBAPPS=true` จะเปิดให้บริการแอปพลิเคชันแบบคลาสสิกอีกครั้งในช่วงเปลี่ยนผ่าน พร้อม
  คำเตือน Tomcat และ WildFly ก็ไม่ให้บริการแอปพลิเคชันเหล่านี้เช่นกัน (ดู
  [ชุดแจกจ่าย Tomcat และ WildFly](#tomcat-and-wildfly-distributions)) ไฟล์ zip ของ Run และ
  Spring Boot starter ยังคงให้บริการอยู่ แต่เลิกแนะนำให้ใช้แล้วและจะนำออกใน
  รุ่นถัดไป (`fasti.webapp.classic.enabled: false` จะปิดใช้งานได้ก่อน)
- เมื่อใช้สคีมาเก่า Fasti จะปฏิเสธการเริ่มทำงานพร้อม `ENGINE-03111` แทนที่จะล้มเหลวในภายหลัง
  (`FASTI_SCHEMA_VERSION_CHECK=warn` เพื่อให้เริ่มทำงานต่อได้)
- นิพจน์ในคิวรีและตัวกรองถูกจำกัดไว้เฉพาะรายการที่อนุญาต (ฟังก์ชันวันที่, ผู้ใช้
  ปัจจุบัน) ตัวกรองที่ใช้ bean หรือฟังก์ชันที่กำหนดเองต้องประกาศสิ่งเหล่านั้นในพร็อพเพอร์ตีการกำหนดค่าเอนจิน
  `allowedExpressionFunctionsInQueries`, `allowedExpressionBeansInQueries` และ
  `allowedExpressionPropertiesInQueries`
- พฤติกรรมของ REST API: ในอิมเมจคอนเทนเนอร์และชุดแจกจ่าย Tomcat และ WildFly ทุกคำขอ ยกเว้นรายการ
  เอนจิน (`/engine`) ต้องมีข้อมูลรับรองแบบ Basic หรือ bearer token ดังนั้นต้องกำหนดค่าไคลเอนต์ REST
  และ worker งานภายนอกให้ส่งข้อมูลเหล่านี้ (โค้ดไม่ต้องเปลี่ยน) ในทุกชุดแจกจ่าย นิพจน์ในคิวรีที่อยู่นอก
  รายการที่อนุญาตจะถูกปฏิเสธด้วย `400` การอ่านหรือแก้ไขไฟล์แนบและความคิดเห็นของงานโดยไม่มีสิทธิ์จะได้รับ
  `403` (เมื่อเปิดการตรวจสอบสิทธิ์) คำขอที่ไม่ถูกต้องบางรายการที่เคยได้รับ `500` จะได้รับ `400` แทน
  (ทรัพยากรการ deploy ที่แยกวิเคราะห์ไม่ได้ ตัวแปรในรูปแบบ Java serialization ที่ถูกห้าม พารามิเตอร์คิวรี
  ผิดชนิด รหัสผ่านที่ละเมิดนโยบายรหัสผ่าน) ดู
  [Differences from Camunda 7](api/README.md#differences-from-camunda-7)
- ค่าเริ่มต้นของอิมเมจ: การอัปเดตสคีมาเป็น `false` (`FASTI_DB_SCHEMA_UPDATE=true` สำหรับฐานข้อมูลใหม่) ไม่มี
  ผู้ใช้สาธิต ตัวอย่างใบแจ้งหนี้ หรือตัวกรอง “งานทั้งหมด” ปิด CORS (`FASTI_CORS_ALLOWED_ORIGINS=*`
  เพื่อเปิดกลับมา) เพิ่ม `/actuator/health` ไฟล์อยู่ภายใต้ `/fasti` (ไฟล์ที่เมานต์ที่
  `/camunda/configuration` จะถูกอ่านด้วย) ไม่มี `--swaggerui`
- OAuth2/OIDC: `camunda-admin` ใน claim ของกลุ่มจะไม่ให้สิทธิ์ผู้ดูแลระบบโดยตัวมันเองอีกต่อไป
  (`fasti.security.oidc.groups.admin`); `group-name-delimiter` เป็นข้อความตามตัวอักษร ไม่ใช่ regex;
  การออกจากระบบต้องใช้ POST จากต้นทางเดียวกัน
- Tasklist ใหม่: ตัวกรองที่ไม่มี `refresh` จะรีเฟรชโดยอัตโนมัติ
- ไฟล์ jar ของ Run คือ `fasti-bpm-run-core.jar`
- การแก้ไขความปลอดภัยเมื่อเทียบกับ 7.24.0 (การตรวจสอบสิทธิ์ไฟล์แนบ/ความคิดเห็น, การตั้งค่าครั้งแรก, ...) อาจทำให้การเรียกบางรายการที่เคยสำเร็จได้รับ 403 ดูหัวข้อ *Security* ใน [CHANGELOG](../CHANGELOG.md) และ <https://fasti.dev/security>

<a id="rollback-to-camunda-724"></a>

## การย้อนกลับไปใช้ Camunda 7.24

หยุด Fasti แล้วเริ่มโหนด Camunda 7.24 บนฐานข้อมูลเดิมอีกครั้ง ทุกสิ่งที่ทำบน
Fasti จะปรากฏที่นั่น สิ่งที่ยังคงอยู่คือ: แถว `fasti.prefs.*` ใน `ACT_ID_INFO` (ค่ากำหนดของ
เว็บ UI ใหม่ ซึ่ง Camunda 7 จะละเว้น) และ `refresh: true` บนตัวกรองที่บันทึกโดย Tasklist ใหม่ซึ่ง
เดิมไม่มีค่านี้ กระบวนการที่ดีพลอยและใช้คุณสมบัติเฉพาะของ Fasti จะไม่ทำงานบน Camunda 7

<a id="mixed-operation-with-camunda-7-nodes"></a>

## การทำงานร่วมกับโหนด Camunda 7

Fasti และ Camunda 7.24 สามารถทำงานบนฐานข้อมูลเดียวกันได้พร้อมกัน (ผ่านการทดสอบแล้ว: ทั้งสองมองเห็น
ข้อมูลของกันและกัน และงานทำงานบนโหนดใดก็ได้) ข้อกำหนด:

- **ระดับประวัติเดียวกัน** (อิมเมจใช้ระดับที่บันทึกไว้), **เขตเวลา JVM เดียวกัน**,
  การตั้งค่ารหัสผ่านและคำนำหน้าตารางเดียวกัน;
- **ตัวประมวลผลงาน:** โดยค่าเริ่มต้น Fasti (อิมเมจ, Run, Spring Boot) จะรับงานจากทุกการดีพลอย เช่นเดียวกับ Run
  ชุดแจกจ่าย Tomcat และ WildFly มีค่าเริ่มต้นเป็น `jobExecutorDeploymentAware=true` (เช่นเดียวกับ Camunda
  7): งาน (ตัวตั้งเวลา, การทำงานต่อแบบอะซิงโครนัส, การลองใหม่) ของการดีพลอยที่ไม่ได้ลงทะเบียนบน
  โหนดนั้น รวมถึงการดีพลอยโดย Run หรือผ่าน REST ก่อนการรีสตาร์ตครั้งล่าสุด **จะไม่
  ทำงาน** เมื่อรับช่วงฐานข้อมูลของ Run ให้ตั้งค่าเป็น `false` ใน `conf/bpm-platform.xml`
  (Tomcat) หรือ `standalone.xml` (WildFly) หากโหนดเดิมรันแอปพลิเคชันกระบวนการที่มีคลาสซึ่ง Fasti ไม่มี (`JavaDelegate`, listener, bean),
  Fasti จะรับงานของโหนดเหล่านั้น ซึ่งจะล้มเหลวและทำให้เกิด incident ดังนั้นให้ตั้งค่า
  `FASTI_JOB_EXECUTOR_ENABLED=false` บน Fasti หรือทำให้ **ทุก** โหนดรับรู้การดีพลอย (ตัวประมวลผลงานของแต่ละโหนด
  จะรันเฉพาะงานของการดีพลอยที่ลงทะเบียนบนโหนดนั้น การดีพลอยผ่าน
  REST จะลงทะเบียนเฉพาะบนโหนดที่รับคำขอนั้นจนกว่าจะรีสตาร์ต) การเรียก REST แบบซิงโครนัส (การทำงานให้เสร็จ,
  การเริ่มอินสแตนซ์) ยังคงรัน delegate บนโหนดที่รับคำขอ — อย่ากำหนดเส้นทางของ
  กระบวนการเหล่านี้ไปยัง Fasti;
- **โหลดบาลานเซอร์:** ใช้ sticky session สำหรับเว็บแอปพลิเคชัน การเรียก REST ที่ยืนยันตัวตนแบบ Basic ไม่จำเป็นต้องใช้;
- เว็บแอปพลิเคชันแบบคลาสสิก (บนโหนด Camunda 7 หรือ Fasti ที่ตั้งค่า
  `FASTI_CLASSIC_WEBAPPS=true`) และเว็บแอปพลิเคชันใหม่ใช้ตัวกรองและผู้ใช้ร่วมกัน

<a id="older-versions-717723"></a>

## เวอร์ชันเก่า (7.17–7.23)

สำรองข้อมูล เรียก `sql/upgrade/<db>_engine_<from>_to_<to>.sql` ตามลำดับจนถึง 7.24 รวมถึง
สคริปต์แพตช์ของเวอร์ชันย่อยปัจจุบันที่ยังไม่ได้เรียกใช้ (จัดส่งไว้ใน `configuration/sql/upgrade` และใน
อิมเมจที่ `/fasti/configuration/sql/upgrade`) ตรวจสอบว่า `ACT_GE_SCHEMA_LOG` มี `7.24.0`;
เริ่ม Fasti ตัวอย่าง 7.22 → 7.24: `postgres_engine_7.22_to_7.23.sql` แล้วตามด้วย
`postgres_engine_7.23_to_7.24.sql` โหนด Camunda ที่เก่ากว่า 7.24 ต้องไม่ทำงานต่อบน
สคีมาที่อัปเกรดแล้ว ยกเว้นภายใต้กฎการอัปเดตแบบทยอยของ Camunda (ต่างกันได้เพียงหนึ่งเวอร์ชันย่อย และ
โหนดเก่าต้องไม่ใช้คุณสมบัติใหม่)

<a id="performance"></a>

## ประสิทธิภาพ

อิมเมจไม่ได้ใช้ค่าเริ่มต้นของ Camunda Run สำหรับตัวประมวลผลงานและพูลการเชื่อมต่ออีกต่อไป (จนถึง Fasti 1.1 ยังใช้อยู่) โดยใช้เธรดงาน 10 เธรด คิว 10 และ 10 งานต่อการดึงงานหนึ่งครั้ง (Camunda Run: เธรดหลัก 3 สูงสุด 10 คิว 3 และ 3 งานต่อครั้ง) และพูลการเชื่อมต่อสูงสุด 20 รายการ ซึ่งเปิดค้างไว้ 10 รายการขณะว่าง (Camunda Run: 10) ให้กำหนดขีดจำกัดการเชื่อมต่อของฐานข้อมูลตามผลรวมของพูลจากทุกโหนด รวมถึงโหนด Camunda 7 ([การปรับแต่งขณะทำงาน](tuning-runtime.md) ภาษาอังกฤษ) หากคุณปรับแต่งพูลการเชื่อมต่อหรือตัวประมวลผลงานของการติดตั้ง Camunda 7 เดิมไว้ ให้นำค่าเหล่านั้นมาใช้ต่อ (`FASTI_DB_CONN_MAXACTIVE`, `FASTI_DB_CONN_MINIDLE`, `CAMUNDA_BPM_JOB_EXECUTION_*`) คำแนะนำเพิ่มเติมอยู่ใน `distro/docker/README.md` หัวข้อ “การปรับแต่งประสิทธิภาพ” Fasti ไม่เปลี่ยนดัชนีของสคีมาเองเลย สำหรับฐานข้อมูลขนาดใหญ่ Fasti มีดัชนีเสริมเป็นสคริปต์ที่ผู้ดูแลระบบเป็นผู้รัน (`/fasti/configuration/sql/optional/<database>_fasti_perf_indexes_create.sql` ดู [performance.md](performance.md)) ซึ่งปลอดภัยเมื่อใช้ร่วมกับโหนด Camunda 7.24 และลบออกได้ด้วย `_drop.sql` ที่คู่กัน

<a id="limits"></a>

## ข้อจำกัด

- รองรับเฉพาะสคีมา 7.24 Community Edition เท่านั้น สคีมาแพตช์ของ Enterprise ยังไม่ได้ทดสอบ
- ทดสอบด้วยอิมเมจคอนเทนเนอร์ (Camunda Run 7.24.0 สร้างฐานข้อมูลและเติมข้อมูลเริ่มต้น → Fasti
  รับช่วงต่อ → กลับไปใช้ Run → ทั้งสองทำงานพร้อมกัน):

  | ฐานข้อมูล | ไดรเวอร์ | การรับช่วงต่อ | การย้อนกลับ | การทำงานร่วมกัน | อัปเกรด 7.23 → 7.24 |
  |---|---|---|---|---|---|
  | PostgreSQL 16 | รวมมาให้ | ผ่าน | ผ่าน | ผ่าน | ยังไม่ได้ทดสอบ |
  | MariaDB 11.8 | MariaDB Connector/J (รวมมาให้) หรือ MySQL Connector/J | ผ่าน | ผ่าน | ผ่าน | ผ่าน |
  | MySQL 8.4 | รวมมาให้ | ผ่าน | — | ผ่าน | ผ่าน |
  | SQL Server 2022 (Developer) | รวมมาให้ (`encrypt=false`) | ผ่าน | ผ่าน | ผ่าน | ยังไม่ได้ทดสอบ |
  | Oracle Database 23ai Free | `ojdbc11` ผ่าน `FASTI_EXTRA_LIB` | ผ่าน | ผ่าน | ผ่าน | ยังไม่ได้ทดสอบ |
  | Db2 12.1 (Community Edition) | `com.ibm.db2:jcc` 12.1.2.0 ผ่าน `FASTI_EXTRA_LIB` | ผ่าน | ผ่าน | ผ่าน | ผ่าน (เฉพาะ schema) |

  Db2: รัน `db2set DB2_EVALUNCOMMITTED=ON DB2_SKIPINSERTED=ON DB2_SKIPDELETED=ON` แล้วรีสตาร์ต
  instance หากไม่ตั้งค่าตัวแปรเหล่านี้ คำสั่งที่ทำงานพร้อมกันจะเกิด deadlock (`SQL0911N`) ในคำสั่ง SQL หนึ่งของเอนจิน
  (`update ACT_HI_TASKINST set REMOVAL_TIME_ … where ROOT_PROC_INST_ID_ = ?`) ซึ่งเกิดบนโหนด
  Camunda 7.24 ด้วยเช่นกัน และเกิดมากที่สุดบนฐานข้อมูลใหม่ที่ยังว่างอยู่ (ในการทดสอบ การทำงานให้เสร็จพร้อมกันส่วนใหญ่ล้มเหลวที่นั่น)
  ทดสอบบน Db2 12.1 Community Edition ด้วยเพจขนาด 4 K, code set UTF-8, isolation CS และ `CUR_COMMIT=ON`
  รวมถึงชุดทดสอบเอนจินของ Fasti และ 15 แพ็กเกจของชุดทดสอบของเอนจิน ค่าเริ่มต้นของ `LOCKTIMEOUT` คือ -1
  (การรอล็อกไม่มีวันสิ้นสุด): ให้กำหนดค่า ไดรเวอร์ (`com.ibm.db2:jcc`) ไม่ได้รวมมาให้ ให้เพิ่มด้วย `FASTI_EXTRA_LIB`
  ยังไม่ได้ทดสอบ: Db2 11.5, Db2 สำหรับ z/OS หรือ IBM i, ขนาดเพจอื่น และการอัปเกรดฐานข้อมูล 7.23 ที่มีข้อมูลอยู่

  นอกจากนี้: โหนด Fasti สองโหนดบน MariaDB (MariaDB Connector/J) ที่ทำงานเดียวกันให้เสร็จและดึงงานภายนอกพร้อมกัน ไม่ทำให้ข้อมูลสูญหายหรือซ้ำกัน ธุรกรรมที่ไม่สำเร็จได้รับข้อผิดพลาด optimistic locking โดย MySQL/MariaDB ต้องใช้ `transaction-isolation=READ-COMMITTED` บน MySQL
  ให้แต่ละเอนจินมีฐานข้อมูลของตนเอง: เอนจิน (ทั้ง Camunda Run และ Fasti) จะค้นหาตาราง
  ในทุกฐานข้อมูลที่บัญชีมองเห็นได้
- ปลั๊กอินและแอปพลิเคชันกระบวนการที่สร้างสำหรับ Camunda 7 ต้องสร้างใหม่โดยใช้อาร์ติแฟกต์ของ Fasti
  เพื่อรันภายใน Fasti ส่วนไคลเอนต์ REST และไคลเอนต์งานภายนอกไม่จำเป็นต้องเปลี่ยนโค้ด แต่เมื่อใช้
  อิมเมจคอนเทนเนอร์ Tomcat หรือ WildFly ต้องกำหนดค่าให้ส่งข้อมูลรับรองแบบ Basic หรือ bearer token
- การตรวจสอบสคีมาอ่านเฉพาะ `ACT_GE_SCHEMA_LOG` เท่านั้น ไม่ได้เปรียบเทียบคอลัมน์
